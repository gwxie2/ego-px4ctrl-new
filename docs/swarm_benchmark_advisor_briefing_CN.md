# 面向导师汇报的 Swarm V1/V2 Benchmark 进展说明（2026-04-03）

## 1. 汇报定位

本文面向导师汇报，不追求穷尽代码细节，而是希望完整说明：

1. 这项工作现在做到哪一步了。
2. 当前结论有哪些是可靠的。
3. 哪些风险已经暴露，后续如何避免走弯路。
4. 这项工作相对于“只会跑 demo”有什么新增价值。

---

## 2. 一句话摘要

当前已经完成了一个可真实落地产物的 V1 / V2 集群 benchmark 体系：它能够在统一顶层入口上自动完成运行、采集、汇总和报告生成；但就算法性能本身而言，当前仍处于“保守基线已建立、高速优化尚未完成”的阶段，V1 当前更稳，V2 潜力更大但也暴露出更明显的不稳定点。

---

## 3. 这次工作真正完成了什么

### 3.1 不是只做了一个脚本，而是补齐了一条完整闭环

过去如果只看系统能否启动，最多只能说明：

- Gazebo / PX4 / planner / px4ctrl 还能拉起来；
- 某些 topic 还在发；
- 某个 demo 能动。

但这类状态并不能支持导师真正关心的问题：

- V1 和 V2 到底谁更稳。
- 哪些问题出在规划器，哪些问题出在控制器或参数。
- 一次实验结束后，是否有可复核的结构化证据。

这次工作的核心推进在于：

- 已把 benchmark 从“手工观察日志”推进到“自动生成真实证据链”。

现在一轮实验结束后，可以自动得到：

- 主时间序列 CSV
- planner event CSV
- replanning CSV
- manifest / summary JSON
- rosbag
- PDF 图表报告

这使得后续讨论不再依赖主观印象，而可以直接落在数据与工件上。

### 3.2 V1 / V2 已经被纳入同一套比较框架

本次 benchmark 不是分别做两套松散脚本，而是统一挂在：

- `swarm_top_level_v1.launch`
- `swarm_top_level_v2.launch`

之上。

这意味着：

- 两个版本可以使用同一套健康检查逻辑。
- 两个版本可以使用同一套 artifact 结构。
- 两个版本可以用同一套离线报表程序进行对比。

对导师汇报来说，这一点非常重要，因为它让“V1 vs V2”不再只是口头比较，而是落在统一 benchmark 体系中的对照实验。

### 3.3 现在已经不是“只能冒烟”，而是“能跑真实全流程”

本次已经完成真实运行并生成最终产物：

- V1：`benchmark_artifacts/20260403_top_level_final/v1/auto_20260403_104104/`
- V2：`benchmark_artifacts/20260403_top_level_final/v2/auto_20260403_104514/`
- 最终报告：`benchmark_artifacts/20260403_top_level_final/report/advanced_benchmark_report.pdf`

这一步的意义是：

- 系统已具备“实验即产出证据”的能力。
- 后续导师要求复查某次结论时，可以直接回到 bag / summary / CSV，而不是回忆当时的终端输出。

## 4. 当前技术状态如何判断

### 4.1 benchmark 体系本身：已经可用

这是本轮最明确的正面结论。

具体来说，当前 benchmark 体系已经具备：

- 顶层统一启动能力
- 自动健康检查能力
- 自动 session 管理能力
- 自动 rosbag 收尾能力
- 自动生成 PDF 报告能力

这一层已经从“试验性工具”进入“可作为后续研究基础设施”的状态。

### 4.2 算法性能本身：仍处于基线阶段

这里需要非常严谨，不能过度汇报。

本轮真实实验的实际规划速度上限仍是：

- `planner_max_vel = 1.2`

因此，本轮结果更适合被表述为：

- 已建立低速 / 保守参数下的 V1 / V2 真实基线；
- 尚不能直接当作高速 benchmark 定论。

换句话说，当前最有价值的结论不是“谁已经赢了”，而是：

- 现在终于有了可靠的比较平台；
- 接下来可以在这个平台上做真正有说服力的高速参数爬升和对比实验。

### 4.3 当前 V1 与 V2 的相对表现

在当前基线下，可以给出比较稳妥的技术判断：

- V1 当前更稳，规划开销更轻。
- V2 当前平均速度更高一些，但稳定性问题更明显。

主要表现为：

- V1 平均 `planner_latency_p95` 明显更低。
- V2 存在较明显的 worst-case 问题：
  - `drone_1` 的 replanning 成功率只有 `39.47%`
  - `drone_2` 的最小安全裕度只有 `0.2712 m`
- 两个版本最终都以 `emergency_stop` 收尾，说明当前仍未达到“可以稳定完成任务”的程度。

因此，对导师最稳妥的表述应当是：

> 当前阶段，V1 更像稳定基线；V2 更像潜力版本，但还需要进一步做稳定性收敛和安全边界调优。

## 5. 这项工作的创新点在哪里

### 5.1 创新点一：把“运行成功”升级为“可度量、可复核、可比较”

以往在多机系统中，常见状态是：

- 系统能飞，但很难精确说明为什么飞得好或不好；
- 某次实验失败后，很难复盘到底卡在 planner、controller 还是仿真链路；
- 不同版本之间经常是“看起来差不多”，缺乏统一数据标准。

本次工作的第一个创新点，是把 benchmark 做成了**结构化证据链**：

- 在线运行时自动记录；
- 离线自动汇总；
- 输出格式稳定，可重复比较。

这意味着后续所有优化都可以绑定到结构化数据，而不是靠经验描述。

### 5.2 创新点二：V1 / V2 共用一套顶层 benchmark 骨架

很多时候，版本比较失败，不是因为算法本身，而是因为：

- 启动入口不一样；
- 参数注入不一样；
- 采集方式不一样；
- 报告口径不一样。

本次工作的第二个创新点，是把 V1 / V2 放入统一入口、统一采集、统一报表的骨架里。

这样后续做对比时，可以明显降低“实验制度本身不公平”的干扰。

### 5.3 创新点三：把 planner 内部行为拉到 benchmark 视野中

本次不只是记录最终轨迹误差，而是把 planner 内部的重规划事件、迭代与时延也纳入了数据链。

这有两个直接价值：

1. 可以更清楚地区分“控制问题”和“规划问题”。
2. 可以在 V2 出现不稳定时，快速定位是 replanning 失败率高、时间代价过高，还是安全间距参数过激。

### 5.4 创新点四：把 benchmark 本身也纳入自动化回归体系

本次新增的不只是最终报告工具，还包括：

- 两步 smoke 测试
- 运行态健康检查
- 自动 artifact 完整性检查

这意味着 benchmark 工具链本身也可以被回归测试，而不是每次都人工猜测“这套脚本今天还能不能用”。

## 6. 最近暴露出的风险，以及为什么它们有价值

### 6.1 风险一：topic 与命名空间很容易让 benchmark 采样失真

本次真实调试中，曾经出现过这样的问题：

- event / replan 数据有了；
- 但主 CSV 只有表头，没有真实采样行。

这类问题非常危险，因为如果不仔细核对，表面上看“系统跑通了、报告也生成了”，实际上数据是不完整的。

这次把它修掉后，后续实验才真正具备可信度。

这类风险对导师汇报的意义在于：

- 我们不仅在做功能，还在补“结论可信度”的基础设施。

### 6.2 风险二：自动起 session 如果设计不严，会产生半截实验数据

本次真实运行中，V2 一度出现：

- 一个完整 session 已经结束；
- 系统又自动拉起第二个半截 session；
- 结果多出 `.bag.active` 与未收尾目录。

这个问题的价值在于，它提醒我们：

- benchmark 不只是采集脚本，更是实验协议的一部分；
- 如果协议不严，数据就会污染。

### 6.3 风险三：当前 speed label 与实际运行速度不一致

当前 benchmark 元数据里仍保留了 `benchmark_default_vmax = 10.0` 的默认值，但这轮真实运行的 `planner_max_vel` 是 `1.2`。

这不是简单命名问题，而是一个**结论口径风险**：

- 如果不说明，外部读者可能会误以为当前已经完成 10m/s 档实验。

因此后续必须把实验标签与真实参数严格对齐，避免对导师形成误导。

### 6.4 风险四：V1 / V2 当前安全阈值不同，直接比较有失公平

当前：

- V1 `swarm_clearance = 0.5`
- V2 `swarm_clearance = 0.35`

这会影响：

- `min_safety_margin`
- `safety_violation_count`

所以如果直接把某些数字拿来横向比较，很容易得出不严谨结论。

这类风险并不说明 benchmark 不行，反而说明 benchmark 已经足够敏感，能暴露“制度不公平”本身。

## 7. 当前最合适的导师汇报口径

建议按以下层次汇报。

### 7.1 第一层：明确成果

可以明确讲：

- 已完成 V1 / V2 集群 benchmark 体系搭建。
- 已在统一顶层入口上跑通真实 benchmark 全流程。
- 已能自动生成 CSV、rosbag、summary JSON、PDF 报告。

这部分可以讲得比较坚定，因为证据已经齐全。

### 7.2 第二层：明确当前结论边界

需要明确讲：

- 当前已完成的是“保守基线 benchmark”，不是最终高速结论。
- 当前的主要价值是：比较框架成熟，数据链闭环完成。
- 后续高速实验将建立在这套已验证平台之上。

这一步能防止导师预期过高，同时也能体现工作节奏是扎实而不是冒进。

### 7.3 第三层：明确当前技术判断

当前最适合的结论是：

- V1 更稳，更像当前阶段的安全基线。
- V2 有更强的速度潜力，但当前在稳定性和安全边界上还需要进一步调优。
- 因此下一阶段工作的重点不是“再写新模块”，而是“基于已有 benchmark 体系做参数爬升与稳定性收敛”。

## 8. 后续最值得做的工作

### 8.1 先做公平基线，再做高速档

下一步不建议直接喊 10m/s，而应先做：

- 同步对齐 V1 / V2 的 `planner_max_vel`
- 同步对齐 `swarm_clearance`
- 同步对齐 benchmark 元数据标签

这样得到的结果才适合正式对比。

### 8.2 先修 V2 的 worst-case，再提速

当前 V2 的主要问题点已经暴露得很清楚：

- `drone_1` replanning 成功率异常低
- `drone_2` 最小安全裕度过低

因此下一阶段应该先围绕 V2 做：

- 避碰间距收紧回保守区
- 重规划压力回调
- 速度分级提升

### 8.3 用门槛推进，而不是凭感觉推进

建议把升档门槛写成制度，例如：

- `replan_success_rate >= 95%`
- `control_lag_p95 < 100ms`
- `min_safety_margin >= threshold + 0.05`
- 无持续 `emergency_stop`

只有达标后再提速，才能避免在大量不稳定数据上浪费时间。

## 9. 导师最关心的问题，当前可以怎样回答

### 问题 1：你们现在到底是“系统能跑”，还是“已经有性能结论”？

建议回答：

- 现在已经不只是系统能跑，而是已经能稳定拿到真实 benchmark 结果。
- 但性能结论目前还是保守基线层面的，尚未上升到最终高速结论。

### 问题 2：V2 到底比 V1 好在哪里？

建议回答：

- 从框架潜力看，V2 有更高速度潜力，也更适合后续做更强的规划优化。
- 但在当前基线参数下，V2 还没有全面优于 V1，尤其稳定性上仍需进一步调优。

### 问题 3：这项工作最核心的研究价值是什么？

建议回答：

- 最核心的价值是，我们已经把多机 planner 对比从“演示级”推进到“可度量、可复核、可回归”的工程与科研基础设施。
- 这会显著提升后续算法优化和论文实验的可信度与效率。

## 11. 本文结论

这轮工作的真正价值，不是单纯多了几张图，而是把 V1 / V2 集群系统推进到了一个更成熟的状态：

- 可以统一启动；
- 可以自动诊断；
- 可以自动收集；
- 可以自动出报告；
- 可以为后续高速优化提供可验证的基准平台。

当前阶段最合适的定位是：

> benchmark 基础设施已经成熟，性能研究正式进入“数据驱动调参阶段”；
> V1 是当前稳定基线，V2 是后续重点优化对象；
> 下一阶段目标不是再证明“系统能飞”，而是证明“在统一基准下，参数和算法如何让系统飞得更稳、更快、更可解释”。
